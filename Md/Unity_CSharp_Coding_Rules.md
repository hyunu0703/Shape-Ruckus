# Unity C# 스크립트 작성 규칙

- 대상: Unity 6000.3.23f1 · C# · 기본 2D 프로젝트
- 적용 범위: 신규 스크립트와 기존 코드의 수정 부분
- 목적: 정상 동작을 우선하고, 현재 기능에 필요한 구조와 안정성을 확보한다.

## 규칙 구분

| 구분 | 의미 |
| --- | --- |
| **필수** | 반드시 지킨다. 충돌이 있으면 요구사항과 기존 동작을 확인하고 변경 이유를 남긴다. |
| **권장** | 기본 선택으로 적용한다. 더 적합한 방법이 있으면 이유를 설명한다. |
| **예외** | 명시한 조건에서 다른 방법을 허용한다. 영향과 검증 결과를 남긴다. |

## 1. 기본 개발 원칙

- **필수**: 다음 순서로 판단한다. **정상 동작 → 구조 → 안정성 → 가독성 → 성능 → 코드 최소화**.
- **필수**: 정상 동작에는 오류 상황과 기존 기능의 유지도 포함한다. 우선순위를 이유로 안정성을 생략하지 않는다.
- **필수**: 요구사항과 완료 조건을 확인한 뒤 구현한다.
- **필수**: 줄 수를 줄이기 위해 의미를 숨기거나 오류 처리를 제거하지 않는다.
- **권장**: 가장 단순하게 요구사항을 충족하는 구현부터 선택한다.
- **예외**: 프레임 시간이나 메모리 제한이 요구사항이면 성능을 설계 단계부터 고려한다.

## 2. 시스템 아키텍처

- **필수**: 클래스는 하나의 명확한 책임을 가진다. 이동, 저장, UI 표시처럼 변경 이유가 다른 책임을 구분한다.
- **필수**: 기능을 추가하기 전에 기존 클래스, 공통 기능, 이벤트, 데이터 구조를 확인한다.
- **필수**: 기존 기능과 같은 시스템을 별도로 구현하지 않는다.
- **권장**: 독립적인 상태·수명·검증이 필요하거나 여러 곳에서 재사용되는 책임을 클래스로 분리한다.
- **권장**: Unity 생명주기나 컴포넌트 접근이 필요하면 `MonoBehaviour`를 사용한다. 순수 계산과 규칙은 일반 C# 클래스를 고려한다.
- **권장**: 기능 조합에는 컴포지션을 우선한다. 객체 간 협력이 필요하면 참조나 의존성 전달을 사용한다.
- **권장**: 서로 다른 구현을 같은 계약으로 다뤄야 할 때 Interface를 사용한다.
- **권장**: 명확한 상위·하위 관계이고 하위 타입이 상위 타입의 계약을 지킬 때 상속을 사용한다.
- **필수**: 미래에 필요할 것이라는 추측만으로 클래스, Interface, Manager, 공통 기반 클래스를 늘리지 않는다.
- **예외**: 요구사항에 구현 교체, 외부 연동, 테스트 격리가 포함되면 구현이 하나여도 Interface를 둘 수 있다.

```csharp
// 좋은 예: 피해를 받는 여러 종류의 대상에 공통 계약 제공
public interface IDamageable
{
    void TakeDamage(int amount);
}

// 나쁜 예: 단일 데이터 보관 클래스에 사용 목적 없는 계약 추가
public interface IPlayerNameProvider
{
    string GetPlayerName();
}
```

## 3. 코드 작성 규칙

| 대상 | 필수 규칙 | 예시 |
| --- | --- | --- |
| 클래스·구조체·열거형 | PascalCase | `PlayerMovement`, `ItemType` |
| Interface | I + PascalCase | `IDamageable` |
| 메서드·프로퍼티·이벤트 | PascalCase | `TakeDamage`, `CurrentHealth`, `HealthChanged` |
| private 필드 | _camelCase | `_moveSpeed`, `_rigidbody` |
| 매개변수·지역 변수 | camelCase | `damageAmount`, `targetPosition` |
| 상수·static readonly 필드 | PascalCase | `MaxInventorySlots` |
| bool 값 | 상태나 판단을 드러내는 이름 | `_isGrounded`, `canAttack`, `HasTarget` |
| MonoBehaviour 파일 | 대표 클래스명과 일치 | `PlayerMovement.cs` |

- **필수**: 멤버의 접근 제한자를 명시한다. 외부 공개 범위를 최소화한다.
- **필수**: Inspector 설정값은 특별한 이유가 없으면 `[SerializeField] private`으로 선언한다.
- **필수**: 외부에서 변경하면 안 되는 상태는 읽기 전용 프로퍼티나 의도가 드러나는 메서드로 제공한다.
- **필수**: 함수는 하나의 목적을 수행한다. 조회 함수가 숨겨진 상태 변경을 하지 않게 한다.
- **필수**: 빈 Unity 이벤트 함수, 사용하지 않는 변수·using, 도달하지 않는 코드, 주석 처리한 구버전 코드를 남기지 않는다.
- **필수**: 의미 있는 수치는 이름 있는 상수나 설정값으로 표현한다.
- **권장**: 들여쓰기는 공백 4칸을 사용하고, 중괄호는 새 줄에 둔다. 기존 파일의 일관된 형식도 존중한다.
- **권장**: 조건문과 반복문에 중괄호를 사용한다. 조기 반환으로 중첩을 줄인다.
- **권장**: 같은 정책의 중복 코드는 한곳으로 모은다. 문장 모양만 비슷한 코드는 억지로 통합하지 않는다.
- **권장**: 타입이 명확할 때 `var`를 사용한다. 축약명보다 역할이 보이는 이름을 사용한다.
- **예외**: Unity 콜백 이름과 외부 API가 요구하는 이름은 해당 계약을 따른다.

```csharp
// 좋은 예: 설정값과 외부 읽기 권한 구분
[SerializeField] private float _moveSpeed = 5f;
private int _currentHealth;

public int CurrentHealth => _currentHealth;

// 나쁜 예: 외부에서 내부 상태를 임의로 변경 가능하며 의미도 불명확
public float s = 5f;
public int hp;
```

## 4. 주석 작성 규칙

- **필수**: 클래스 선언 위에 `/// <summary>`로 책임과 주요 역할 작성.
- **필수**: 직접 작성한 함수에는 `//`로 역할을 짧게 설명. 한 줄 설명으로 충분.
- **필수**: 모든 주석은 `입력 방향 저장`처럼 짧은 구 형태로 작성. `~한다`, `~된다`, `~입니다` 같은 서술형 표현 사용 금지.
- **필수**: 주석에 마침표 사용 금지. `//`, `/// <summary>`, 데이터 흐름 설명, TODO에 동일하게 적용.
- **필수**: 중요한 데이터 흐름에는 입력 출처, 변환 이유, 결과 전달 위치를 필요한 만큼 설명.
- **필수**: 코드 변경 시 관련 주석도 함께 수정.
- **권장**: 코드 내용의 반복보다 제약과 선택 이유 중심으로 설명.
- **필수**: TODO에는 남은 작업과 완료 조건 명시. 설명 없는 임시 코드 방치 금지.
- **예외**: 자동 생성 코드와 외부 패키지 코드는 규칙 적용 대상에서 제외.

```csharp
/// <summary>
/// 입력 이동 방향 보관 및 2D 물리 이동에 전달
/// </summary>
public sealed class PlayerMovement : MonoBehaviour
{
    private Vector2 _moveInput;

    // 입력 방향 저장
    public void SetMoveInput(Vector2 input)
    {
        // 프레임 단위 입력 수신 후 FixedUpdate에서 저장값 사용
        _moveInput = Vector2.ClampMagnitude(input, 1f);
    }
}
```

## 5. 자료구조 및 알고리즘

| 자료구조 | 권장 용도 | 주요 시간 복잡도 및 주의점 |
| --- | --- | --- |
| `Array` | 크기가 고정된 순차 데이터 | 인덱스 접근 O(1), 값 검색 O(n), 크기 변경 시 새 배열 필요 |
| `List<T>` | 순서를 유지하는 가변 목록 | 인덱스 접근 O(1), 끝 추가 분할 상환 O(1), 검색·중간 삽입·삭제 O(n) |
| `Dictionary<TKey, TValue>` | 고유 키로 값 조회 | 조회·추가·삭제 평균 O(1), 최악 O(n), 키 중복 불가 |
| `HashSet<T>` | 중복 제거와 포함 여부 확인 | 조회·추가·삭제 평균 O(1), 최악 O(n), 순서 보장에 의존 금지 |
| `Queue<T>` | 먼저 들어온 작업부터 처리 | 삽입 분할 상환 O(1), 제거 O(1) |
| `Stack<T>` | 최근 작업부터 처리 | 삽입 분할 상환 O(1), 제거 O(1) |

- **필수**: 순서, 중복 허용 여부, 조회 방식, 예상 데이터 수에 맞춰 선택한다.
- **권장**: 반복 실행되는 경로는 O(1), O(log n), O(n) 알고리즘을 우선 검토한다.
- **필수**: 빅오만으로 성능을 단정하지 않는다. 호출 빈도, 데이터 크기, 할당, 실제 측정값을 함께 판단한다.
- **권장**: 대량 추가량을 예상할 수 있으면 컬렉션 용량을 미리 지정한다.
- **필수**: 순회 중 구조 변경은 해당 컬렉션이 허용하는 방식으로 처리한다.
- **권장**: Dictionary에서 키가 없을 수 있으면 `TryGetValue`를 사용한다.
- **예외**: 초기화 시 한 번 수행하는 정렬은 O(n log n)을 허용한다. 작은 고정 데이터의 O(n²)도 단순성과 측정 결과에 따라 허용한다.

```csharp
// 좋은 예: 같은 키를 한 번만 조회
if (_items.TryGetValue(itemId, out Item item))
{
    item.Use();
}

// 나쁜 예: 같은 키를 두 번 조회
if (_items.ContainsKey(itemId))
{
    _items[itemId].Use();
}
```

## 6. Unity 성능 최적화

- **필수**: 처리할 일이 없는 `Update`, `FixedUpdate`, `LateUpdate`는 제거한다.
- **권장**: 상태 변화 통지는 이벤트를 사용한다. 지속 계산이 필요한 동작만 매 프레임 처리한다.
- **필수**: 반복 사용하는 컴포넌트는 적절한 초기화 시점에 조회하고 캐싱한다.
- **필수**: 매 프레임 `Find` 계열 검색이나 반복적인 `GetComponent` 호출을 하지 않는다.
- **권장**: 선택적 컴포넌트 확인에는 `TryGetComponent`를 사용한다.
- **권장**: 빈번한 실행 경로에서 LINQ, 클로저, 박싱, 문자열 조합, 임시 컬렉션으로 생기는 GC 할당을 줄인다.
- **권장**: 자주 생성·파괴되는 객체는 비용을 확인한 뒤 풀링한다. 반납 시 상태와 구독을 초기화한다.
- **필수**: 기본 2D 프로젝트에서는 `Rigidbody2D`, `Collider2D`, `Physics2D`를 사용한다. 2D와 3D 물리 API를 혼용하지 않는다.
- **권장**: 입력은 선택한 입력 시스템의 콜백이나 `Update`에서 수집하고, 지속적인 물리 이동은 `FixedUpdate`에서 적용한다.
- **필수**: 물리 이동은 선택한 Rigidbody2D 모드와 API의 의미에 맞춘다. 속도에 시간을 다시 곱하지 않는다.
- **권장**: 충돌 레이어와 물리 쿼리 범위를 필요한 대상으로 제한한다.
- **필수**: 성능 문제는 Unity Profiler로 확인한다. 변경 전후를 같은 조건에서 비교한다.
- **권장**: 목표 기기의 빌드에서 CPU 시간, GC Alloc, 메모리, 물리 비용을 확인한다.
- **예외**: 초기화나 드문 UI 처리의 작은 할당은 복잡도를 늘려 제거하지 않는다. 측정 결과로 결정한다.

## 7. 안정성 및 예외 처리

- **필수**: 필수 참조는 `Awake` 등 사용 전 시점에 검증한다. 누락 시 원인을 알리고 해당 동작을 중단한다.
- **권장**: 같은 오브젝트의 필수 컴포넌트는 `[RequireComponent]`와 참조 검증을 함께 사용한다.
- **필수**: 선택적 참조의 null 처리와 필수 설정 누락을 구분한다. 무조건적인 null 반환으로 오류를 숨기지 않는다.
- **필수**: `UnityEngine.Object` 참조는 파괴 상태를 반영하는 `== null` 또는 Unity의 bool 판정을 사용한다. `?.`와 `??`에 파괴 상태 판정을 맡기지 않는다.
- **필수**: 이벤트 구독과 해제 시점을 짝지어 관리한다. 활성화 중 구독은 `OnEnable`/`OnDisable`을 기본으로 한다.
- **필수**: 중복 구독을 막고, 해제할 익명 함수는 델리게이트 참조를 보관한다.
- **필수**: 다른 오브젝트의 `Awake` 실행 순서에 의존하지 않는다. 필요하면 명시적인 초기화 절차를 둔다.
- **권장**: 자기 참조 초기화는 `Awake`, 활성 상태 구독은 `OnEnable`, 초기 활성 객체 간 준비 후 처리는 `Start`에 배치한다.
- **필수**: 중복 실행되면 안 되는 Coroutine은 실행 핸들이나 상태로 제어한다. 완료·중단 시 상태도 정리한다.
- **필수**: 비활성화·파괴 시 Coroutine, 비동기 작업, 외부 이벤트가 객체에 접근할 수 있는지 확인한다. 필요한 중단·취소·해제를 명시한다.
- **필수**: `Destroy` 호출 후 해당 객체를 계속 사용하지 않도록 흐름과 참조를 정리한다.
- **필수**: 예외는 복구하거나 원인을 설명할 수 있는 경계에서 처리한다. 빈 `catch`로 무시하지 않는다.
- **권장**: 잘못된 인수, 인덱스, 중복 실행은 진입 지점에서 검증한다.
- **예외**: 외부 파일이나 네트워크처럼 실패 가능한 작업에는 예외 처리와 사용자에게 보일 복구 동작을 둔다.

## 8. 기존 코드 수정 및 AI 작업 범위

- **필수**: 수정 전에 호출 위치, 데이터 흐름, 이벤트 구독, 관련 Scene·Prefab·직렬화 필드를 확인한다.
- **필수**: 요청한 동작을 만족하는 최소 범위만 변경한다. 무관한 시스템과 파일은 수정하지 않는다.
- **필수**: 기존 public API, 이벤트 계약, 저장 데이터 형식은 유지한다.
- **필수**: 직렬화 필드 이름 변경은 Inspector 데이터 유실 여부를 확인한다. 필요하면 `FormerlySerializedAs`와 관련 에셋 검증을 함께 적용한다.
- **필수**: 기존 시스템을 재사용한다. 같은 역할의 Manager, 입력 처리, 인벤토리 등을 새로 만들지 않는다.
- **필수**: 불필요한 파일, 패키지, 테스트용 Scene, 임시 로그, 생성물을 추가하지 않는다.
- **필수**: 사용자의 기존 변경을 되돌리거나 덮어쓰지 않는다.
- **권장**: 버그 수정과 대규모 리팩터링을 분리한다. 구조 개선은 현재 문제 해결에 필요한 범위로 제한한다.
- **필수**: Codex는 실제 변경 파일, 변경 이유, 검증 결과, 남은 제한을 보고한다. 실행하지 않은 테스트를 통과했다고 쓰지 않는다.
- **예외**: 요청 해결에 API 변경이나 범위 확대가 반드시 필요하면 영향과 대안을 먼저 설명하고 승인된 범위에서 진행한다.

## 9. 개발 및 테스트 순서

1. **필수 — 요구사항 분석**: 입력, 기대 결과, 실패 조건, 기존 동작과의 관계를 정리한다.
2. **필수 — 구조 설계**: 책임, 참조 관계, 데이터 소유자, 초기화 순서를 정한다. 기존 구현을 먼저 찾는다.
3. **필수 — 구현**: 정상 경로부터 완성하고, 경계 조건과 실패 처리를 추가한다.
4. **필수 — 테스트**: 컴파일 오류와 Console 오류를 확인하고 실제 사용 흐름을 검증한다.
5. **필수 — 버그 수정**: 재현 조건을 확보하고 원인을 수정한 뒤 해당 흐름을 다시 확인한다.
6. **권장 — 최적화**: Profiler로 병목을 찾고 필요한 부분만 개선한다. 동작을 다시 확인한다.

- **필수**: 변경과 관련된 정상 입력, 빈 데이터, 경계값, 중복 호출을 확인한다.
- **필수**: 생명주기를 바꿨다면 활성화·비활성화 반복, 파괴, Scene 전환을 확인한다.
- **권장**: 순수 계산과 규칙은 Edit Mode 테스트, 컴포넌트·물리·생명주기는 Play Mode 테스트를 고려한다.
- **권장**: 재발 위험이 큰 버그와 핵심 규칙에는 의미 있는 자동 테스트를 추가한다.
- **예외**: 문서 수정처럼 실행 동작에 영향이 없으면 실행 테스트를 생략하고 링크·형식·내용을 검토한다.
- **필수**: 실행 환경이 없으면 확인한 범위와 미검증 항목을 명확히 남긴다.

## 10. 최종 검토 및 Git

- **필수**: 작업 시작과 종료 시 `git status`를 확인한다. 최종 diff에서 의도하지 않은 변경을 제거한다.
- **필수**: Unity 에셋을 추가·이동할 때 `.meta` 파일을 함께 관리한다. 기존 GUID를 불필요하게 바꾸지 않는다.
- **필수**: `Library`, `Temp`, `Logs`, `obj`, 로컬 빌드 산출물과 비밀 정보를 커밋하지 않는다.
- **필수**: Scene·Prefab·프로젝트 설정의 변경은 요청과 관련 있는지 확인한다.
- **권장**: 하나의 커밋은 하나의 설명 가능한 변경으로 구성한다.
- **필수**: 커밋 제목은 `type: 변경 내용` 형식으로 작성한다. 제목은 실제 변경을 짧고 구체적으로 표현한다.
- **권장**: 추가 설명이 필요하면 본문에 변경 이유, 영향, 검증 결과를 적는다.
- **필수**: Codex는 사용자가 요청한 경우에만 커밋·푸시한다.
- **예외**: 저장소에 별도로 정해진 커밋 규칙이 있으면 해당 형식을 우선한다.

| type | 용도 | 제목 예시 |
| --- | --- | --- |
| `feat` | 기능 추가 | `feat: 아이템 획득 처리 추가` |
| `fix` | 버그 수정 | `fix: 재활성화 시 공격 이벤트 중복 구독 수정` |
| `refactor` | 동작을 유지하는 구조 개선 | `refactor: 피해량 계산 책임 분리` |
| `perf` | 성능 개선 | `perf: 주변 대상 검색의 임시 할당 감소` |
| `docs` | 문서 변경 | `docs: Unity C# 작성 규칙 추가` |
| `test` | 테스트 변경 | `test: 인벤토리 최대 수량 검증 추가` |
| `chore` | 설정·유지보수 | `chore: 로컬 빌드 출력 제외 설정` |

## 최종 코드 검토 체크리스트

해당하지 않는 항목은 N/A로 표시한다. 미검증 항목은 이유를 남긴다.

- [ ] 요구사항과 완료 조건을 만족한다.
- [ ] 기존 기능과 공개 API의 동작을 유지한다.
- [ ] 기존 시스템을 재사용하며 중복 구현이 없다.
- [ ] 클래스와 함수의 책임이 명확하고 불필요한 추상화가 없다.
- [ ] 명명, 접근 제한자, 직렬화 필드 규칙을 지킨다.
- [ ] 클래스 summary, 함수 주석, 중요한 데이터 흐름 설명이 최신이다.
- [ ] 모든 주석이 서술형 표현과 마침표 없이 짧은 구 형태로 작성되어 있다.
- [ ] 자료구조와 알고리즘이 데이터 크기와 호출 빈도에 적합하다.
- [ ] 빈 Update, 반복 컴포넌트 검색, 불필요한 할당이 없다.
- [ ] 2D 물리 API와 입력·물리 처리 시점을 올바르게 사용한다.
- [ ] null, 초기화 순서, 경계값, 필수 참조 누락을 처리한다.
- [ ] 이벤트와 Coroutine의 중복 및 수명 종료 처리가 안전하다.
- [ ] 컴파일과 관련 동작 검증을 수행하고 결과를 기록했다.
- [ ] 성능 변경은 필요한 경우 Profiler로 전후를 비교했다.
- [ ] Scene·Prefab 참조와 직렬화 데이터가 유지된다.
- [ ] 요청과 무관한 수정, 임시 파일, 로그, 비밀 정보가 없다.
- [ ] 최종 diff, 에셋의 .meta 파일, 커밋 대상 범위를 확인했다.
